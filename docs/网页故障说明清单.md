## 3. 故障详述

### F-001 提示「登录已过期，请重新登录」并被强制登出

**现象**
已登录的教师/管理员在使用约 1 小时后，任意操作弹出「登录已过期，请重新登录」，并被强制退出登录。

**根因链路**
1. 令牌有效期被写死为 **3600 秒（1 小时）**：
   - `backend/src/config/app.js:51`
     ```js
     expiresIn: toNumber(process.env.JWT_EXPIRES_IN, 3600)
     ```
   - `backend/.env.example:14` → `JWT_EXPIRES_IN=3600`
2. 签发端同样使用该值：`backend/src/controllers/authController.js:19`
   ```js
   return jwt.sign(payload, config.jwt.secret, { expiresIn: config.jwt.expiresIn })
   ```
3. 过期后：
   - **API 侧**：`backend/src/middleware/authMiddleware.js:49-55` 中 `jwt.verify` 抛错 → 返回 `401 / AUTH_FAILED / 登录已过期，请重新登录`。
   - **路由侧**：`src/router/guards.ts:40-43` 检测 `isTokenExpired()` 为真 → 直接 `authStore.logout()`。
4. 前端 `src/utils/api.ts:169-175` 捕获任意 401 → `authStore.logout()` + 抛出「登录已过期，请重新登录」。

**为什么 1 小时后必然发生**
仓库中没有任何自动续期机制（见 F-004），因此 1 小时是硬上限，无法通过「保持页面打开」延长。

**修复建议（P1）**
- 提高令牌有效期：将 `JWT_EXPIRES_IN` 改为秒数（如 `604800` = 7 天），**不要写成 `7d`**（见 F-003）。
- 或实现滑动续期：在 `guards.ts` 中于令牌剩余寿命低于阈值时调用 `refreshToken()`。

### F-002 密码输错却提示「登录已过期，请重新登录」（语义塌陷）

**现象**
学生使用错误密码登录（例如测试账号 `99999999`），页面显示「登录已过期，请重新登录」，而不是「学号或密码错误」。

**根因链路**
1. 后端**登录接口本身用 401 表示"凭证错误"**：
   - `backend/src/controllers/authController.js:65-78`（学生）、`184-203`（教师）、`245-257`（管理员）
     ```js
     return res.status(401).json({
       success: false,
       error: 'INVALID_CREDENTIALS',
       message: '学号或密码错误',
     })
     ```
2. 前端**把"所有 401"一律当成令牌过期**：`src/utils/api.ts:169-175`
   ```ts
   if (response.status === 401) {
     const authStore = useAuthStore()
     if (authStore.isLoggedIn) authStore.logout()
     throw new ApiError(401, 'AUTH_EXPIRED', '登录已过期，请重新登录')
   }
   ```
3. 登录流程同样走 `request()` → `handleResponse()`，因此后端返回的 `message: '学号或密码错误'` 在到达 UI 前就被**丢弃并覆盖**。
4. `src/stores/auth.ts:121-124` 将覆盖后的消息写入 `error.value`，UI 最终展示「登录已过期，请重新登录」。

**影响**
- 用户看到的是误导性提示，无法判断是"密码错误"还是"会话过期"。
- 排查"学生登录失败"时极易被这条假消息带偏（**本次排查即由此产生**）。

**修复建议（P1）**
在 `handleResponse` 中按 `error` 字段分流，仅当 `AUTH_REQUIRED` / `AUTH_FAILED` 时判定为会话问题；`INVALID_CREDENTIALS` 应原样透传后端 `message`。示例：
```ts
if (response.status === 401) {
  const data = (await response.json().catch(() => null)) as { error?: string; message?: string } | null
  if (data?.error === 'INVALID_CREDENTIALS') {
    throw new ApiError(401, 'INVALID_CREDENTIALS', data.message || '账号或密码错误')
  }
  const authStore = useAuthStore()
  if (authStore.isLoggedIn) authStore.logout()
  throw new ApiError(401, 'AUTH_EXPIRED', data?.message || '登录已过期，请重新登录')
}
```

### F-003 `JWT_EXPIRES_IN=7d` 配置无效

**现象**
运维将 `JWT_EXPIRES_IN` 配置为 `7d`，期望令牌 7 天有效，实际仍是 1 小时。

**根因**
`backend/src/config/app.js:15-18` 的 `toNumber()` 仅接受纯数字：
```js
function toNumber(value, fallback) {
  const n = Number(value)
  return Number.isFinite(n) ? n : fallback
}
```
`Number('7d')` → `NaN` → 回退到默认值 `3600`。**配置被静默忽略，无任何告警**。

**修复建议（P2）**
- 短期：统一使用秒数（`604800`）。
- 长期：为 `JWT_EXPIRES_IN` 增加 `ms`/`d` 单位解析，或在解析失败时**启动即报错**而非静默回退。

### F-004 令牌刷新链路失效（`refreshToken` 为死代码）

**现象**
页面长时间挂起后仍需重新登录，`/api/auth/refresh` 从不被调用。

**证据**
全仓检索 `refreshToken` 仅命中定义处，**无任何调用方**：
```
src/stores/auth.ts:170  async function refreshToken(): Promise<void> {
src/stores/auth.ts:271    refreshToken,   // 仅导出
```
同样，`isTokenExpired()` 仅被 `src/router/guards.ts:40` 使用，且用途是"过期即登出"，而非"过期前续期"。

**修复建议（P1）**
在路由守卫或请求拦截器中接入自动续期；并确保后端 `/api/auth/refresh` 路由已注册。

### F-005 偶发未携带令牌的请求被拒

**现象**
应用初始化早期发起的请求偶发返回 401，并被提示「登录已过期」。

**根因**
`src/utils/api.ts:23-34` 的 `getAuthHeaders()` 在 Pinia 未安装或令牌为空时**静默返回空对象**：
```ts
function getAuthHeaders(): Record<string, string> {
  try {
    const authStore = useAuthStore()
    if (!authStore.token) return {}
    return { Authorization: `Bearer ${authStore.token}` }
  } catch {
    return {}   // Pinia 未安装 → 无鉴权头
  }
}
```
请求因此不带 `Authorization` 头 → 后端 `requireAuthMiddleware` 返回 `401 / AUTH_REQUIRED / 需要登录` → 前端仍显示「登录已过期，请重新登录」。

**修复建议（P2）**
区分"确实未登录"与"初始化竞态"：初始化完成前不发起鉴权请求，或对 `AUTH_REQUIRED` 做重试而非直接登出。

### F-006 整站不可用 / 「本电脑离线」（环境层）

**现象**
手机端经常显示"本电脑离线"，网页无法访问。

**根因**
主机（学校办公电脑，DESKTOP-8QRO363）被**长时间断电离线**，属运行环境问题，非代码缺陷。详见第 4 节实测数据。

### 4.3 结论

1. **主要离线原因是主机整机断电，而非空闲休眠。** 每次恢复开机都伴随 `Kernel-Power 41`（"系统未正常关机便重新启动"）事件，说明是**突然断电**，不是正常关机流程。
2. **用户从未主动关机属实。** `User32 1074`（用户/进程发起的关机）最后一条停留在 **2026-09-15 17:01**，此后无任何主动关机记录。
3. **工作日恢复时间集中在 06:30–07:15**（09-22 06:57、09-23 06:49、09-24 06:55、09-28 06:59、09-29 06:40、09-30 07:10、10-08 06:32）。
4. **节假日离线更长**：09-26→09-28 跨越周末（37.6 h）；09-30→10-02、10-02→10-04、10-04→10-08 连续跨越国庆假期，最长 91.5 h。
5. **对夜间自动化任务的影响（重要）**：夜间任务窗口为 22:00–08:00，而主机典型离线区间约为 16:00/20:00 → 次日 06:30/07:15，**两者高度重叠**。若不改变供电或唤醒条件，夜间任务实际可执行窗口仅约 06:30–08:00。
